# Кандзи дня

Спокойное мобильное веб-приложение для изучения одного кандзи в день —
для полных новичков, ещё не знающих кану. Интерфейс на русском,
японский показывается с каной и ромадзи. Без очков, стриков и наград.

## Состав

**Фронтенд** — React + TypeScript + Tailwind CSS v4 + shadcn/ui на Vite.
Четыре экрана: тропа, знак, разбор, порядок черт.

**Бэкенд** — FastAPI + PostgreSQL 16 + Redis 7 в Docker. Анонимные
пользователи (без регистрации), интервальные повторения по SM-2.

---

## Фронтенд

Работает поверх API — статических данных и localStorage больше нет.

```bash
npm install
npm run dev     # dev-сервер на :5173
npm run build   # сборка
```

Бэкенд должен быть запущен: Vite проксирует `/api` на `127.0.0.1:8082`
(см. `vite.config.ts`). Прокси нужен не только для удобства — благодаря
ему запрос остаётся однодоменным, и кука `device_id` ходит без CORS.

**Развёртывание фронтенда пока не описано в compose.** Собранная статика
из `dist/` может раздаваться либо хостовым nginx напрямую, либо
отдельным контейнером; выбор за вами, поскольку nginx на сервере ваш.
Единственное требование — `/api/` должен проксироваться на бэкенд с
того же домена, иначе кука перестанет ходить.

## Бэкенд

### Запуск

```bash
cp .env.example .env          # и подставить свои значения
docker compose up -d
docker compose run --rm backend alembic upgrade head
docker compose run --rm backend python -m scripts.seed
```

API поднимется на `http://127.0.0.1:8082`, документация (вне production) —
на `/api/docs`.

Проверка:

```bash
curl http://127.0.0.1:8082/api/health
curl http://127.0.0.1:8082/api/kanji?limit=3
```

### Разработка

Для локальной работы есть отдельный файл с монтированием исходников и
авто-перезагрузкой. Он назван **не** `docker-compose.override.yml`
намеренно: override подхватывался бы автоматически, и его легко применить
на сервере по невнимательности.

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
```

Без монтирования исходников Alembic сгенерирует миграцию внутри
контейнера, и она исчезнет вместе с ним при `--rm`, поэтому новые
миграции создаются только так:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml run --rm backend \
  alembic revision --autogenerate -m "описание"
```

Применяются они уже обычной командой — но **образ нужно пересобрать**,
иначе файл миграции в него не попадёт:

```bash
docker compose build backend
docker compose run --rm backend alembic upgrade head
```

То же правило действует для `seed`: он читает `data/kanji.json` из
образа, поэтому после пересборки справочника образ тоже надо собрать
заново.

Миграции намеренно не запускаются при старте приложения: при нескольких
воркерах это даёт гонку.

### Сеть и безопасность

- `backend` опубликован строго на `127.0.0.1:8082`. Явный адрес обязателен:
  без него Docker пишет правила прямо в iptables в обход ufw, и порт
  оказывается открыт всему интернету.
- `db` и `redis` наружу не публикуются вообще — только внутренняя сеть.
- uvicorn запускается с `--proxy-headers --forwarded-allow-ips="*"`. Это
  безопасно ровно потому, что контейнер недоступен извне; если порт
  когда-нибудь откроют шире, клиент сможет подделать свой IP и обойти
  лимитер.
- От хостового nginx ожидается **перезапись** `X-Real-IP`. Заголовок
  `X-Forwarded-For` дописывается, и его левая часть контролируется
  клиентом.

### Redis

Только кэш и счётчики лимитера, поэтому персистентность отключена
(`--save "" --appendonly no`) и тома нет. Ограничение памяти — 256 МБ с
политикой `allkeys-lru`.

Побочный эффект политики: под давлением памяти может быть вытеснен
счётчик лимитера, и лимит на время ослабнет. При наших объёмах это
маловероятно, но это осознанный компромисс.

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Живость процесса, без обращения к зависимостям |
| GET | `/api/kanji` | Справочник, пагинация и фильтр по JLPT |
| GET | `/api/kanji/{id}` | Один иероглиф |
| GET | `/api/trail` | Данные главного экрана: лента изученных, знак дня |
| GET | `/api/lesson/today` | Повторения на сегодня плюс новый знак дня |
| GET | `/api/reviews/due` | Карточки, готовые к повторению |
| POST | `/api/reviews/{kanji_id}` | Ответ на карточку, пересчёт SRS |
| GET | `/api/stats` | Краткая статистика устройства |

Клиенту стоит слать заголовок `X-Timezone` с таймзоной IANA — от неё
зависит граница суток для дневных счётчиков. Фронтенд делает это сам в
`src/lib/api.ts`.

Номер знака («день 9») теперь означает порядок изучения **этим
устройством**, а не общий календарный день курса: с появлением SRS
каждый идёт своим темпом. Номер приходит с `/api/trail` и передаётся
между экранами через состояние роутера; при заходе по прямой ссылке
его нет, и подпись просто короче.

### Алгоритм повторений

SM-2 с тремя оценками вместо канонических шести: `again` / `good` / `easy`
(внутренние q = 2 / 4 / 5). Шесть градаций — избыточный выбор для
новичка и противоречат спокойному тону приложения.

Полноценных learning steps нет: при ответе «не помню» карточка
возвращается через 10 минут. Из-за этого `interval_days` и
`next_review_at` могут расходиться — первое хранит интервал по SM-2 в
днях, второе фактический момент показа.

### Справочник кандзи

В базе все **2136** иероглифов дзёё, но в уроки попадают только записи с
выверенным вручную русским значением (`is_published`). Сейчас таких
**81** — это весь уровень JLPT N5 плюс один знак сверх него, то есть
около трёх месяцев ежедневных уроков.

Причина в том, что открытого источника «кандзи → русское значение» не
существует. Автоматический вывод из словаря слов даёт правдоподобную
ложь: 山 получал значение «спекуляция; риск» вместо «гора», 子 — «крыса,
знак зодиака» вместо «ребёнок». На четырнадцати базовых кандзи три грубо
неверных.

Поэтому автовывод ничего не публикует — его догадка кладётся в отдельное
поле `meaning_suggested` как черновик для вычитки. Значение для урока
берётся только из `backend/data/kanji_ru.json`.

Слова-примеры тоже пришлось вычитывать руками. Автоматический отбор
ранжировал по средней частотности составляющих иероглифов, а самые
частотные — 一 и 人, поэтому он выбирал 一手, 一見, 一時 вместо 手紙,
花見, 時間. Плюс часть переводов в источнике начинается с пометки, и
на выходе получалось «1» или «(кн.)» вместо смысла.

Надёжные данные (чтения он/кун, число черт, JLPT, частотность, пути
черт) приходят из KANJIDIC2 и KanjiVG и есть на все 2136.

**Известный пробел:** пояснения к отдельным чертам (`instruction` у
каждого элемента `strokes`) сейчас пустые — они были в старых
статических данных фронтенда и не перенеслись в конвейер. Общее
описание порядка черт (`writing_note`) есть у всех опубликованных.

Пересборка справочника:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml run --rm backend \
  python -m scripts.build_dataset --with-strokes
docker compose run --rm backend python -m scripts.seed
```

`seed.py` работает только через UPSERT и никогда не удаляет строки: у
`reviews.kanji_id` внешний ключ с каскадом, поэтому пересоздание
справочника молча стёрло бы весь прогресс пользователей.

### Источники данных

- [KANJIDIC2](https://www.edrdg.org/wiki/index.php/KANJIDIC_Project) — чтения, значения, число черт
- [KanjiVG](https://kanjivg.tagaini.net/) — порядок черт
- [AnchorI/jlpt-kanji-dictionary](https://github.com/AnchorI/jlpt-kanji-dictionary) — уровни JLPT, частотность, слова с русским переводом
